# 機車與電池序號管理規格

日期：2026-10-11
狀態：使用者已確認本書面規格；尚未實作。

## 目的與已確認範圍

使用原廠序號追蹤每一台機車及每一顆電池，從收貨、銷售到保固與維修都能對應到同一件實物。保留既有商品條碼掃描、分類選貨、多人登入及權限分級。零件與用品維持數量管理，不強制序號。

本次是跨進貨、庫存、銷售、保固與備份的架構變更，不以單一保固文字欄位取代實物追蹤。

## 方案選擇

- 採用：獨立序號清單，連結品項、收貨及銷售；銷售與保固另存序號快照。可查在庫及已售實物，能防止同一實物重複售出。
- 不採用：只在保固備註填序號。雖然較少改動，但無法核對收貨數量、重複銷售及在庫序號。
- 暫不採用：把業務資料遷到雲端資料庫。這是另一個同步與後端權限專案，不是本次必要條件。

## 審閱時需特別確認的規則

以下具體規則已隨本規格確認：

1. 機車與電池依分類強制序號管理，不另加可關閉的開關。
2. 原廠序號全店不可重複，包含已售及已移出紀錄。保留大小寫與前導零，僅去除首尾空白；相同字串視為重複。如不同廠牌可能使用相同序號，應在實作前改為「品項＋序號」唯一。
3. 序號商品結帳必選客戶，避免售出後無法連結保固對象。有設定正整數保固月數才自動產生保固；月數為零仍保存客戶與銷售序號關聯。
4. 既有庫存未全數補齊序號前，該品項暫停出貨，但其他品項仍可使用。
5. 庫存調整移出的實物另外標記「已移出」，不冒充已售；移出須填原因。退貨、重新入庫及換貨不在第一版。

## 資料與一致性

沿用現有 Inventory 純函式、整份 state 驗證及 IndexedDB 單筆交易儲存，不新增套件、資料庫 store 或 Supabase 結構。

新增 state.serials 清單，每筆包含：

- id、itemId、serialNumber。
- status：in_stock／sold／removed。
- purchaseId（進貨收貨時提供）、createdAt、createdBy。
- saleId、customerId、soldAt（已售時提供）。
- removedAt、removedBy、removalReason（移出時提供）。

銷售明細保存 serialIds 與 serialNumbers 陣列；每筆序號保固保存 serialId 與 serialNumber 快照。保固案件繼續連結 warrantyId，不重建維修資料模型。

新資料需驗證 ID、序號唯一性、品項關聯、狀態及銷售／客戶關聯；不能靠畫面 disabled 避免無效資料。已售序號不可再次售出或移出，已移出序號不可售出。序號不可透過一般編輯更換所屬品項或覆寫已售歷史。

對序號商品，庫存必須為安全非負整數。在庫序號數不得大於品項庫存；小於庫存只允許作為既有資料待補登狀態。新收貨、銷售及移出必須同時更新庫存、序號和相關紀錄，任何一步失敗都不保存部分結果。

## 既有庫存與資料保護

- 舊備份缺少 serials 時視為空清單；舊銷售及保固沒有序號時顯示「未登錄」，不自動編造序號或改寫歷史。
- 庫存管理提供品項序號補登，顯示庫存、已登錄在庫數及待補登數。補登只能填補差額，不增加庫存、不產生進貨紀錄。
- 舊庫存不是整數時顯示需先核對的錯誤，禁止自動取整。可由店長依實物更正庫存，不能低於已登錄在庫數。
- 新增機車、電池品項若填初始庫存，必須同時填等量序號；也可先以零庫存建立再收貨。
- 已有序號的品項不可刪除或改分類以繞過序號管理；必要時提示使用者保留歷史紀錄。
- 沿用匯入前備援下載。匯入沒有序號的舊備份時，明確警告這是整份還原，會取代現有序號、銷售及保固資料，不做不可靠的合併。
- 保留 localStorage 舊資料作既有回復備援，不清除瀏覽器資料。

## 進貨與庫存操作

進貨維持整張一次收貨。草稿不先占用序號；按收貨時列出每項機車／電池的應收數量，逐件輸入或掃描序號，每次 Enter 收下一個。收貨前驗證每項序號數量等於應收數量，且本單內與既有清單均無重複。收貨後不得重複收貨。

既有一般入庫也需輸入等量序號，出庫需選等量在庫序號並填原因；盤點調整增加庫存需填新增序號，減少庫存需明確選擇移出序號。不得透過品項直接改庫存或舊的單筆銷售介面略過這些驗證。待補登品項的減少盤點僅可更正未識別差額，已識別實物的減少必須明確移出。

## 銷售操作

保留商品條碼掃描及分類選貨入口。選到機車／電池後，顯示該品項在庫序號，可掃描或選擇；商品條碼欄與序號欄分開，避免混淆。指定數量須等於所選不同序號數；已在購物車中的序號不可再加入其他列。

購物車顯示商品、序號、單價、數量、小計。零件及用品照舊，可與序號商品混合一次結帳。移除購物車商品只釋放選擇，不改庫存；放入購物車不算售出，也不做跨分頁保留。

結帳重新核對現有品項、序號狀態、數量、客戶與庫存，一次儲存銷售、出庫、序號已售狀態及保固。儲存失敗保留購物車，庫存與序號不變；登出清除未結帳的序號選擇。

## 保固與查詢

同一銷售明細買兩顆電池，產生兩筆各自帶序號的保固，不再共用一筆保固。沿用目前購買日、月數及月底日期計算規則，不自行增加保固月數。

手動新增機車／電池保固必須選擇已售且有客戶關聯的序號，帶入對應客戶及品項，不得把在庫商品當成已售；同一序號第一版只允許一筆保固，不做續保。舊無序號保固仍可查詢與維修，不強迫補造序號。

在庫存管理提供序號清單與補登入口；保固頁搜尋涵蓋序號，詳情顯示序號、客戶、銷售日期、到期日期及既有維修案件。一般庫存清單仍不顯示成本。

沿用既有角色分工：店長維護初始庫存、補登、更正與移出；可銷售人員可以選擇在庫序號結帳並依既有權限操作保固。既有允許收貨的角色維持不變，操作人使用登入身分，不可手填冒用。

## 修改範圍與驗證

- inventory.js：state 正規化、序號規則、品項新增／編輯／刪除、收貨、所有庫存異動與銷售入口、保固建立／搜尋、備份。
- app.js、index.html、style.css：補登、收貨輸入、購物車序號指定、查詢及明確錯誤提示；新控制項納入登入鎖定與登出清理。
- storage.js：以測試確認現有單筆儲存可保留所有新增欄位，沒有必要則不改儲存實作。
- 現有測試及 fixtures：補齊新契約；新增序號、收貨、混合結帳、保固及匯入回復測試。
- 更新資源版本，避免瀏覽器沿用舊腳本。

測試涵蓋：舊資料可讀、前導零保留、重複序號拒絕、錯品項序號拒絕、數量不符、舊庫存補登不增量、重複收貨、已售重售、混合購物車、每件一筆保固、缺客戶、移出、刪除／改分類防繞過、儲存失敗不半套更新、匯入匯出往返、登出清空草稿，以及原有一般用品銷售不退化。

## 第一版界限

不做換貨、退貨、序號重新入庫、原廠保固平台串接、序號標籤列印及雲端業務資料同步。IndexedDB 仍屬單一瀏覽器資料；本次序號驗證不提供跨電腦共用庫存或跨分頁並行交易安全，操作上應只用一個工作分頁並定期匯出備份。
