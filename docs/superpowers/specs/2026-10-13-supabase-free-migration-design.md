# Supabase Free 多機資料移轉設計

## 目標

以 Supabase Free 的 PostgreSQL 作為核心庫存系統唯一正式資料來源，讓受授權人員可從電腦與手機登入並操作同一份品項、庫存、客戶與銷售資料；既有 IndexedDB 資料在切換前完整備份，且在驗證完成前不刪除。

## 範圍與限制

- 沿用現有 Supabase 專案、帳號登入、角色與 RLS 資料庫設計。
- 前端只使用 publishable key 與使用者工作階段；禁止新增或提交 service-role／secret key。
- Free 方案用於驗證階段；專案閒置可能暫停，且不把它視為唯一備份來源。
- 第一版必須在線才可寫入；IndexedDB 僅作遷移來源與本機唯讀快取，不再作跨裝置權威資料。
- 不包含離線寫入佇列、衝突合併、多店別、付費方案升級或自訂網域。
- 供應商、採購、序號、保固與報價暫不移轉；雲端模式必須隱藏或停用其操作，避免產生只留在單一裝置的資料。

## 架構

前端登入後從 Supabase 載入符合既有 `Inventory` state 結構的資料。每次異動先由 PostgreSQL 的 RLS 和交易函式驗證帳號、角色及庫存，再回傳成功狀態；前端只有在雲端成功後更新畫面與本機快取。結帳與庫存扣減必須使用單一資料庫交易，避免多裝置同時操作導致負庫存。

## 遷移流程與安全閘門

1. 管理員在來源電腦先匯出完整 JSON，並驗證可重新讀取；此備份不可上傳至公開 GitHub。
2. 檢查現有 Supabase 專案、已套用 migration、RLS、grants、登入函式及部署後端；未通過時停止，不寫入任何營運資料。
3. 以管理員身分在受限匯入流程驗證 JSON state；雲端先建立受權限保護的備份，再在單一交易內寫入資料。
4. 以來源電腦重新登入，比對品項、庫存、客戶與銷售筆數及關鍵數值。
5. 以手機與第二台電腦各自登入，驗證兩者讀到同一資料；測試一筆可回復的低風險庫存操作，以及同品項並行結帳不足時第二筆被拒絕。
6. 僅在所有驗證通過後，將正式讀寫切換為雲端；IndexedDB 舊資料仍保留，不自行刪除。

## 存取控制

- 管理員可管理品項、成本、帳號、匯入與稽核紀錄。
- 店員只能讀取必要庫存、建立允許的銷售／客戶／報價資料；不得讀成本、管理帳號或刪除營運資料。
- 停用帳號要撤銷工作階段；所有資料表維持 RLS 與最小 grants。
- 重要異動保留操作者、時間與稽核紀錄。

## 驗收條件

1. 三個不同裝置登入後均看見同一份雲端品項、庫存、客戶與銷售資料。
2. 遠端裝置完成庫存異動後，其他登入裝置重新載入即可取得正確結果。
3. 同品項庫存不足時，併發的第二筆扣庫存操作被資料庫拒絕，庫存不為負數。
4. 店員無法透過 UI 或資料 API 讀取成本或執行管理員操作。
5. 遷移失敗時，來源 IndexedDB 與已匯出的 JSON 都仍可使用。
6. 自動化測試覆蓋核心雲端 state 讀寫、RLS／權限拒絕與庫存交易原子性；手機與第二台電腦完成實機 smoke test。

## 升級條件

完成上述驗證後，若系統成為日常營運唯一資料來源，或需要自動備份與不中斷服務，升級 Supabase Pro 並啟用其備份能力，再決定是否停用舊本機資料來源。
