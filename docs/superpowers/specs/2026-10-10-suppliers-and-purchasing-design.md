# 供應商與進貨管理第一版規格

日期：2026-10-10
狀態：使用者已確認正式規格；Native 實作及獨立審查修正完成，95 項測試通過。實際瀏覽器操作未驗證。

## 目的與已確認範圍

在現有原生 HTML／JavaScript 系統加入供應商、單一供應商品項關聯、進貨及付款管理。每張進貨單先存草稿，整張確認收貨才增加庫存；不分批收貨。收貨後以本次進貨單價更新品項成本，不改售價、料號、條碼及歷史銷售成本快照。付款只有未付款／已付款，不分次付款。

採用既有單頁分頁、純資料操作函式及 IndexedDB 整份狀態儲存方式，不引入依賴或另建後端。相較直接修改庫存，此方式保留進貨依據；相較完整採購會計系統，第一版不處理退貨、應付帳款報表、稅額、折扣、運費及會計分錄。

以下為依既有程式擬定的具體規則，隨本文件一併審閱：只有店長可操作新增模組；供應商僅停用、不刪除；付款限已收貨單標記且第一版不撤銷已付款狀態。

## 現況與安全邊界

- 業務資料來源是 `inventory.js` 定義的狀態，由 `storage.js` 寫入 IndexedDB；備份使用 `toBackup`／`validateState`。
- 登入角色已有 admin／店員，但本機業務資料並未透過伺服器授權儲存。新增模組在畫面及事件入口檢查 admin，這是操作限制，不是可抵抗開發者工具的安全邊界。
- 本次不修改 Supabase 資料表或雲端功能，不宣稱多人共享、同步或跨裝置一致性。維持單一電腦、單一操作分頁；多分頁同時編輯仍有覆寫風險。

## 供應商管理

新增「供應商管理」分頁，店長可新增、編輯、搜尋及停用。

資料：`id`（UUID）、`name`、`contact`、`phone`、`address`、`taxId`、`note`、`active`、`createdAt`、`updatedAt`。

名稱必填，其餘文字欄位選填、前後去空白；統編有填時須為 8 碼數字（只驗格式，不查營業登記）。以 UUID 識別供應商，不以名稱作唯一鍵。搜尋名稱、聯絡人、電話與統編，提供啟用／停用篩選。

停用不刪除資料或解除既有品項關聯，不可建立新進貨單或新增指派至該供應商；既有關聯仍顯示「已停用」，允許改派或清空。停用不阻止停用前已儲存草稿的收貨與付款，以便完成既有交易。

## 品項與供應商

品項新增 `supplierId`，空字串代表尚未指定。舊資料缺此欄位時補空字串，不批次指派。

品項編輯表單新增單選供應商；同一品項僅一個供應商，可改派。一般庫存清單僅增加供應商名稱，不增加成本欄位；供應商編輯不更動品項名稱及電池規格命名規則。

進貨單只可選其供應商目前綁定的品項，未指派品項須先至庫存管理指派。為避免已存草稿與後續操作不一致，草稿編輯儲存及確認收貨時均重新檢查品項存在且供應商關聯符合。品項已改派時提示修改草稿，不默默換供應商。

## 進貨管理與資料

新增「進貨管理」分頁，店長可建立／編輯／刪除草稿、查看單據、確認收貨及標記付款；列表可依單號、供應商名稱搜尋，並依草稿／已收貨與付款狀態篩選。

一張單屬於一家供應商，可加入多個不同品項。切換供應商且已有明細時，確認後清空明細；取消則保留原供應商及明細。同品項重複加入時提示，改原明細數量即可，不建立多筆不同成本。

進貨單資料：

- `id`（UUID）、`number`（`P` + 台北日期 YYYYMMDD + 3 碼流水號，例如 `P20261010001`）。按現存同日單據最大序號加一；超過 999 拒絕建立；刪除最高序號草稿後可再利用該號，UUID 才是永久識別碼。
- `supplierId`、`supplierSnapshot`：名稱、聯絡人、電話、地址、統編。
- `status`：`draft`／`received`；`paymentStatus`：`unpaid`／`paid`。
- `lines`：`itemId`、`itemName`、`sku`、`barcode`、`quantity`、`unitCost`、`subtotal`。
- `total`、`note`、`createdAt`、`updatedAt`、`receivedAt`、`paidAt`、`createdBy`、`receivedBy`、`paidBy`。未發生的時間與操作者為空字串，操作者從目前登入使用者取得，不由表單輸入。

每張草稿至少一項明細，數量須為正整數；單價須為有限、非負且最多兩位小數，允許零元進貨。預設帶入品項目前成本，可自行修改；若既有成本超過兩位小數，明確四捨五入成兩位並在表單顯示後再儲存。以整數分計算小計／總額，拒絕超過安全整數範圍的金額或數量。總額是明細小計合計，不自行加入稅額。

儲存草稿時擷取供應商及品項快照；再次編輯儲存時刷新快照，確認收貨則沿用最後儲存版本。供應商或品項日後改名不改既有單據；銷售、報價及保固快照也不回寫。

## 收貨與付款狀態

草稿只保存單據，不改庫存、成本或庫存異動。可刪除草稿，需確認。

確認收貨前顯示供應商、總數及總額，再次確認；重驗整張單、品項及關聯，任一錯誤則整張拒絕。成功時同一份下一狀態包含：

1. 各品項庫存增加進貨數量，成本改為該明細單價。
2. 每項新增一筆既有格式的 `in` 庫存異動，備註包含進貨單號，並以可選的 `purchaseId` 關聯進貨單；舊異動缺此欄位補空字串。
3. 單據變成 `received`，記錄收貨時間與操作者。

以上透過一次 IndexedDB 狀態寫入一起完成；儲存失敗則不更新記憶體狀態或顯示成功，保留原草稿。收貨中停用操作按鈕，狀態函式拒絕對已收貨單再次收貨，避免連點或重試造成重複入庫。

已收貨單唯讀，不允許直接改明細、改供應商或刪除。第一版沒有收貨撤銷／退貨，誤收時需另外做既有庫存調整並在備註寫明原單號；這不會撤銷原進貨紀錄或自動還原成本，畫面需提醒。

付款預設未付款，只有已收貨單可確認「標記已付款」。不扣庫存、不改成本、不產生金流；記錄付款時間與操作者。第一版不提供分次付款或撤銷已付款，重複標記拒絕執行。零元單同樣可標記已付款。

## 相容性、刪除與備份

根狀態新增 `suppliers`、`purchases`，舊資料缺少時預設空陣列。正規化及匯入檢查 ID 唯一性、外鍵、列舉狀態、時間、明細數量、金額合計、付款／收貨一致性；不得忽略不合法資料或部分匯入。

有進貨單引用的品項不得刪除（包括草稿）；先刪除或編輯草稿解除引用，已收貨紀錄永久保留引用。單據中保留快照供歷史顯示，供應商僅停用，因此不會因刪除供應商失去關聯。庫存異動若填 `purchaseId`，須引用存在的已收貨單。

JSON 匯出／匯入包含供應商、品項關聯、進貨單及異動關聯，沿用既有匯入前保護備份。匯入舊備份仍屬整份取代，會以空陣列取代新模組資料；警告需明確指出，不做隱藏合併。

## 實作範圍與驗收

預計修改 `inventory.js`、`app.js`、`index.html`、必要的 `style.css`，及相關資料、導覽、儲存測試；`storage.js` 若既有整份狀態交易已足夠則不修改。更新前端腳本版本避免舊快取。

驗收包含：

- 供應商新增、編輯、搜尋、停用及欄位驗證；店員看不到入口且操作事件拒絕非店長。
- 單一供應商關聯、未指派／停用品項、切換供應商時保留或清空明細的確認行為。
- 多品項草稿儲存／編輯／刪除不影響庫存，數量、重複品項與金額檢查。
- 整張收貨正確增加庫存、更新成本、建立異動；無效品項、改派供應商、重複收貨及寫入失敗均不部分入庫。
- 已收貨單不可改刪；付款限制與時間／操作者記錄正確，付款不影響庫存。
- 歷史銷售成本、報價、品項電池命名及 13 碼料號／Code 128 功能不退化。
- 舊資料載入、新資料備份往返、非法備份拒絕及匯入前保護；全套 `node --test` 與 JavaScript 語法檢查通過。
- 如環境允許，瀏覽器驗證分頁、收貨確認、付款及重新整理後資料保存；未能實測時明確列出限制，不以單元測試替代實機驗證。
