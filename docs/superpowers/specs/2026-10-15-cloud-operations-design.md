# 雲端營運模組設計規格

## 目的

將供應商、進貨、報價、保固與送修納入 Supabase，讓正式營運資料在已授權裝置間一致；瀏覽器 IndexedDB 僅作快取與備援，不再作唯一正式資料來源。

## 範圍

- 雲端同步：品項、成本、庫存異動、客戶、業務、銷售、月銷量、供應商、進貨、報價、保固、送修、序號。
- 手機版：僅顯示月銷量，不顯示或開放其他管理頁面。
- 桌面版：啟用供應商、進貨、報價、保固與送修頁面，移除其「準備中」狀態。
- IndexedDB：保留作離線讀取快取、本機備援與首次資料匯入來源。

## 權限

| 模組 | 店長 | 店員 |
| --- | --- | --- |
| 品項、成本、庫存異動 | 讀寫 | 讀取 |
| 供應商、進貨、付款、收貨 | 讀寫 | 不可存取 |
| 客戶、業務、銷售 | 依既有規則 | 依既有規則 |
| 報價、保固、送修 | 新增、查看、編輯、刪除 | 新增、查看、編輯 |

刪除報價、保固與送修限店長；所有表格使用 RLS 與最小資料庫授權雙重限制，前端隱藏不作為權限邊界。

## 資料模型

### 既有資料表補齊

- `quotations`、`quotation_lines`：納入讀取與交易式寫入，保留客戶、業務、品項、名稱、單價與小計快照。
- `warranties`、`warranty_cases`：納入讀取與交易式寫入，補齊實物序號、銷售來源、替換關係與案件快照所需欄位。
- `sales`、`sale_lines`、`inventory_transactions`：維持既有原子銷售與庫存異動流程，並與保固、序號關聯。

### 新增資料表

- `suppliers`：名稱、聯絡人、電話、地址、統編、備註、啟用狀態、建立／更新時間與建立者。
- `purchases`：單號、供應商、供應商快照、草稿／已收貨狀態、付款狀態、金額、收貨與付款操作者、時間與備註。
- `purchase_lines`：進貨單、品項、品項快照、數量、單價、小計。
- `inventory_serials`：品項、原廠序號、狀態、收貨／銷售／保固關聯與時間，供 QR Code、銷售、保固使用。
- `app_migrations`：模組遷移紀錄，防止同一批 IndexedDB 資料被重複匯入。

所有公開 schema 的新資料表都啟用 RLS；明確撤除 `anon` 存取權，僅授與 `authenticated` 所需的最小 CRUD 權限。

## 原子操作

### 收貨

收貨使用受權限保護的資料庫函式，一次完成：

1. 鎖定指定進貨單並確認狀態是草稿。
2. 驗證店長權限、明細與序號數量。
3. 增加品項庫存、寫入庫存異動與序號。
4. 將進貨單設為已收貨並記錄操作者與時間。

同一張進貨單再次收貨或其他裝置同時收貨時，資料庫拒絕第二次操作。

### 報價與保固

報價、保固、送修以交易式 RPC 寫入主檔與明細；更新與刪除都檢查角色及關聯完整性，不接受前端自行指定操作者或跨資料關聯。

## 首次遷移與備援

1. 僅店長可啟動首次遷移。
2. 先下載時間戳記本機備份，保留原始 IndexedDB 資料。
3. 驗證本機資料完整性後以單一交易匯入缺少的模組資料。
4. 寫入模組遷移紀錄；後續登入一律讀雲端資料，避免重複匯入。
5. 失敗時不標記完成，保留本機來源與雲端既有資料。

## 使用者介面與同步

- 桌面版解除供應商、進貨、報價、保固頁面停用狀態。
- 每次成功寫入後重新讀取雲端快照，其他登入裝置重新載入後可看到一致資料。
- 本機讀取失敗時維持唯讀快取提示，不允許把過時本機狀態覆寫到雲端。
- 手機版路由維持導向月銷量，其他管理頁面不提供入口。

## 驗證與交付標準

- 新增資料庫 RLS allow／deny 測試，覆蓋未登入、店員、店長三種身分。
- 測試收貨重複提交與兩個並行操作只會增加一次庫存。
- 測試供應商、進貨、報價、保固、送修的讀寫及關聯完整性。
- 用兩個已授權帳號於不同裝置驗證雲端讀取與權限。
- 驗證首次遷移產生本機備份、可重試、且不重複匯入。
- 部署前執行完整測試、Supabase 安全 advisor 與 GitHub Pages 實機驗證。
