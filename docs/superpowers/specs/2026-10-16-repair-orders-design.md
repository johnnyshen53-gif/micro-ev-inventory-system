# 維修單獨立模組設計規格

## 目的與已確認範圍

建立可跨裝置使用的付費維修單，涵蓋接修、檢查／報價、完工扣料、全額收款與列印。維修收入不併入現有月銷售或業務員績效；免費保固更換維持既有「出保固」流程。

- 可選既有會員，或只輸入臨時客人的姓名與電話；不可默默替臨時客人建立會員。
- 送修物件填車牌或原廠序號，至少一項；另記車型／品名及故障描述。
- 員工可建立、編輯、報價、確認完工並扣料、標記全額收款；每一步記錄操作人與時間。
- 用料可含零件、用品與電池；電池須逐件選定在庫原廠序號。第一版不把整台機車當維修用料。
- 付款只分未收款、已全額收款；不做訂金、部分付款、退款或與銷售合併報表。
- 電腦版新增維修管理；保留目前手機版的頁面限制。

## 方案與既有資料邊界

採獨立維修單與明細表，沿用既有會員、品項、庫存與登入權限。不可把付費維修塞進保固案件，亦不可只存瀏覽器。所有維修寫入與完工扣料以伺服器資料庫為準，不從前端快照推算後直接覆寫庫存。

現有序號僅接受在庫、已售、移出、出保固；現有保固只接受人工或銷售來源，且序號保固要求「已售」序號。付費維修裝上的電池不是一般銷售，也不是無保固移出，因此需新增可追溯至維修單的「維修領用」序號狀態與「維修」保固來源，更新相應資料庫約束、讀取映射與本機驗證規則；不能偽造銷售單或重用與事實不符的來源。

## 資料與狀態

- 維修單：穩定 ID、自動且唯一的單號、選填會員 ID、客戶姓名／電話快照、車牌與原廠序號（至少一項）、車型／品名、故障描述、檢查／處理說明、工資、總額、狀態、付款狀態、建立／更新／報價／完工／收款時間與對應操作者。金額使用非負數值，所有重新計算由資料庫根據明細與工資完成，不信任前端傳入總額。
- 維修用料明細：品項 ID、名稱／料號快照、正整數數量、非負單價、小計；電池明細另存實際領用的序號 ID 與文字快照。完工後保留歷史快照，不因品項改名或售價更動而改寫舊單。
- 維修狀態只允許 `接修中 → 已報價 → 已完工`，以及完工前取消；已取消不得完工或收款。未完工可修正資料與用料；已完工的客戶、用料、工資、金額與序號不可修改。付款獨立為未收款／已全額收款，僅已完工單可標記全額收款；第一版不支援取消已收款。
- 客戶轉換：臨時客人平時不需會員；若用料中的新電池須建立保固，完工前必須明確選擇既有會員或先在客戶管理建立會員。保固期沿用品項保固月數；設定為零或缺失時阻止該電池完工並提示先確認保固設定，避免產生無到期日的保固。

## 原子完工與權限

新增受保護的資料庫寫入入口。完工時在同一交易鎖定維修單、涉及品項與序號，重新驗證登入者為啟用員工、單據未完工／取消、庫存足夠、電池序號仍在庫且數量正確、會員與保固設定有效。成功後一次寫入庫存異動、扣除庫存、標記電池序號為維修領用、建立新電池保固、更新維修單及審計資訊；任一步失敗全部回滾。重送完工要求不得再次扣料或建保固，並回傳明確錯誤。

維修表啟用 RLS，匿名者無權存取；已登入且啟用的員工可讀取及執行核准操作。敏感寫入須在資料庫再次驗證權限，不能只靠隱藏按鈕。公開瀏覽器僅使用可公開的 Supabase key，不含管理員密鑰。列印只供已登入者在應用程式內操作，不產生公開可分享的客戶資料網址。

## 畫面與資料流

1. 「維修管理」顯示可搜尋清單，以單號、電話、車牌或原廠序號尋找維修單；可進入詳情及查看狀態、總額、付款狀態。
2. 建立時選會員或輸入臨時客人資料，填送修物件與故障；檢查後加入用料、單價、工資與處理說明，確認報價。報價與編輯階段不動庫存。
3. 員工確認完工前選定每顆電池的在庫序號；系統顯示即將扣除的項目與數量。伺服器確認成功後重新讀取維修單與庫存；失敗保留草稿並顯示原因，不把單據誤標為完工。
4. 完工後可標記全額收款。瀏覽器列印頁包含單號、客戶與聯絡電話、車牌／原廠序號、故障／處理說明、用料與電池序號、工資、總額及狀態；明顯標示未完工或未收款，不另加 PDF 套件。

## 實作範圍與驗收

- 資料庫：新增維修單／明細、序號與保固來源關聯、必要約束與索引、RLS、原子寫入入口及審計欄位；以 migration 管理。
- 前端：新增維修頁面與列印樣式、雲端讀寫介面，更新 `index.html`、`app.js`、`cloud-data.js` 與現有序號／保固映射及驗證所在檔案；保留目前手機版導航限制。測試涵蓋 UI、資料庫、權限與快取版本。
- 驗收：建立會員或臨時客人維修單；報價不扣庫存；零件與選定電池完工後僅扣一次；電池保固可在既有保固頁查詢；庫存不足、重複完工、序號重複或已領用、臨時客人電池保固及未設定保固期均拒絕且不留下半筆資料；收款與月銷售分離；跨裝置一致；列印清晰且不公開客戶資料。
- 本規格只定義實作方向。正式 Supabase migration、Commit、Push 與部署均須在完成測試並取得使用者明確同意後分階段執行。
