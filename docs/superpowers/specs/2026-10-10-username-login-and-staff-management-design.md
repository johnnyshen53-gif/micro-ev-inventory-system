# 帳號登入、店長專屬業務員管理與閒置登出

## 狀態與目標

需求已確認；本文件待使用者審閱，尚未實作或部署。所有人改用帳號與密碼登入，網頁不再接受 Email 登入。只有啟用中的店長（admin）能建立業務員登入身分、設定初始密碼、重設密碼與停用帳號。一般業務員沿用 clerk 權限。加入連續五分鐘未操作自動登出。

## 現況與範圍

目前 Supabase Auth 使用 Email 密碼；profiles 保存角色與啟用狀態。業務清單與庫存等營運資料仍存在各瀏覽器 IndexedDB，沒有完成跨裝置同步。新增帳號管理以雲端身份資料為準，不能以本機業務清單決定登入權限。

本次不重做營運資料同步、不增加新角色、不提供自行註冊、不刪除歷史業務或交易、不遷移歷史操作人快照。此改動不能讓同一台電腦內的 IndexedDB 成為具後端隔離的多使用者資料庫；本機資料存取與成本隔離的既有限制需另案處理。

## 方案選擇

採用受信任的 Supabase Edge Function 解析帳號並驗證原有 Auth 密碼。帳號對應的 Auth Email 僅留在後端，登入成功才回傳建立前端工作階段所需資訊，不回傳帳號與 Email 對照。

不採用匿名可查詢的帳號對照表，避免洩露 Email；不把既有使用者改成假 Email，避免原密碼與使用者 UUID 的遷移風險。Supabase 底層仍可保留 Email 身分；「不提供 Email 登入」指本系統介面與帳號登入端點，不宣稱停用 Supabase 原生 Email 驗證能力。

## 身分資料與規則

- 雲端建立受保護的登入帳號對照，連結 Auth UUID。使用者 UUID、profiles.role 與 active 保持為既有授權依據。
- 帳號採 3–32 字元，英文字母、數字、底線與連字號；去除首尾空白後轉小寫，大小寫視為同一帳號。唯一性由資料庫強制，不接受 @，不直接以姓名作登入識別。
- 顯示姓名可使用中文；帳號與姓名分開。第一版建立後不提供改帳號，停用後保留帳號不重複利用，避免操作人混淆。
- 密碼至少 12 字元並符合專案 Auth 政策；不自行存放明文或自訂雜湊，不寫入日誌、稽核摘要、IndexedDB 或備份。
- 登入清單保存身份狀態；本機業務資料可增加可選 authUserId，舊資料不依姓名自動配對。店長明確選擇連結，既有報價的業務 ID 與快照不變。
- 不允許一般業務員建立帳號或修改權限；保留 admin/clerk 兩級。網頁只建立 clerk，不提供自行升級為 admin 的功能。首位店長或其他店長身分由受信任管理流程維護。

## 登入與後端安全

1. 登入頁只顯示「帳號」「密碼」，使用正確的 username/current-password autocomplete。
2. 登入端點驗證輸入、解析受保護對照，以一般 Auth 密碼驗證流程登入；不可用管理金鑰取代密碼驗證或直接產生任意使用者 session。
3. 驗證啟用狀態與 profiles 後才接受登入。不存在、密碼錯誤或停用均顯示「帳號或密碼不正確，或帳號已停用」，不透露帳號是否存在。
4. 登入端點以持久化、跨執行個體的限制防暴力嘗試：每帳號每 15 分鐘最多 10 次失敗（包含進行中的驗證）、全站每 15 分鐘最多 50 次登入請求；不依賴來源 IP 或轉送標頭。超限回傳一般限制訊息，不將密碼記錄至任何儲存。2026-10-11 使用者同意此替代方案：大量錯誤嘗試可能讓全站暫時無法登入；既有工作階段與資料不因此刪除。
5. 帳號管理每次檢查有效 JWT 及資料庫中當下 active/admin，不信任前端角色或 user_metadata；匿名、停用或 clerk 直接呼叫亦拒絕。公開表啟用 RLS，私有對照不提供匿名讀取。
6. 管理金鑰只存在 Edge Function 環境，不進入網頁。回應與日誌不洩露密碼、Email 對照或 token；登入回應禁止快取。
7. 停用或重設密碼時撤銷既有工作階段；受保護後端操作仍檢查 active/session，不能假設已簽發的 JWT 會立即失效。最後一位啟用店長不能被停用或降級。

## 店長操作與業務連結

業務人員頁加入店長專用的雲端帳號區，顯示姓名、帳號、角色與啟用狀態。新增時輸入姓名、帳號與初始密碼；既有業務可由店長明確連結帳號。一人最多一個登入連結，一個登入身分最多連結一筆業務。

新 Auth 身分、對照及 profile 全部成功才顯示建立完成；使用請求識別避免重送重複建立。跨 Auth 與資料庫失敗採補償／重試，未完成的身分保持不可登入，不留下可登入的孤兒帳號。雲端建立成功但本機連結儲存失敗時，明示帳號已建立、連結未完成，允許重新連結而不是再建帳號。

重設密碼輸入新密碼並確認，不顯示舊密碼。停用登入帳號需確認，不刪除或重寫歷史交易。本機「停用業務」與雲端「停用登入」是不同動作，介面明確區分，避免本機儲存失敗造成雲端狀態誤判。

新操作紀錄保存穩定 UUID 與姓名／帳號快照，優先顯示姓名，其次帳號，不再以 Email 作新快照。舊 Email 或其他歷史快照原樣保留，不猜測操作者或批次重寫。

## 五分鐘閒置登出

- 登入成功開始計時；滑鼠移動、點擊、鍵盤、觸控與捲動更新最近活動時間。背景同步或網路請求不算操作。
- 使用絕對時間檢查五分鐘期限。背景分頁、休眠恢復、下一次互動時先檢查是否已逾期，不能靠遲到的輸入延長已逾期工作階段。
- 同瀏覽器、同來源的頁籤共享最近活動與鎖定狀態；重新整理不能重設已過期時間。其他裝置獨立計時。
- 到期先隱藏營運畫面並禁止操作，再登出本瀏覽器 session；顯示「閒置超過 5 分鐘，請重新登入」。斷線或撤銷失敗仍保持本機鎖定，重新整理不能自動恢復舊 session。
- 登出清除未送出的購物車、表單及敏感畫面狀態；已儲存資料及既有備援不刪除，已開始的儲存須完成或明確報錯，不悄悄取消成功交易。
- 此為前端閒置鎖定，不是可抗修改前端的伺服器五分鐘 session 到期機制。不宣稱憑證在五分鐘時全球失效。

## 切換與復原

部署後端與資料結構後，先為既有啟用身分分配不衝突帳號；店長帳號由本人指定，不由 Email 猜測。保留原 UUID、密碼與權限，以測試身分及店長實際驗證完成後，才切換正式網頁為帳號登入。

切換前備份設定、身份對照及營運資料；不可刪除 localStorage/IndexedDB。部署失敗可回復舊版網頁及登入入口，原 Auth 身分不變。回復不撤銷已完成的帳號停用或密碼重設。沒有確認店長新帳號可用，不得移除現有入口造成鎖店。

## 驗證與驗收

1. 正確帳號與原密碼可登入；輸入 Email、不存在帳號、錯誤密碼、停用帳號均拒絕。大小寫／空白正規化及重複帳號有測試。
2. 店長可建立 clerk、連結業務、重設密碼與停用；clerk、匿名、偽造角色、停用店長的直接 API 呼叫均失敗。
3. 建立部分失敗、重送、最後店長保護、重設後舊 session、登入速率限制有後端整合測試；公開 API 不洩露對照、密碼或管理金鑰。
4. 用假時鐘驗證 4:59 可操作、5:00 登出、互動延長、背景／休眠、刷新、跨頁籤、斷線及重複登出；重新登入不殘留前人的未儲存內容。
5. 原庫存、銷售、報價、業務與進貨紀錄及成本快照不變，執行全套既有測試；用專用測試帳號驗證瀏覽器流程，不用正式庫存試結帳。
6. 部署前核對 Supabase migration 歷史與安全 advisor；測試通過與正式部署分開回報，不能把本機通過當作雲端可用。
