# 多人登入與權限分級設計

## 目標與範圍

將目前單一電腦、單一瀏覽器的機車店庫存系統升級為可由多台電腦或手機共用同一份中央資料的網頁系統。第一版使用帳號與密碼登入，提供管理員與店員兩種角色。

本階段包含登入、權限、雲端資料庫、既有資料遷移、線上同步與異動稽核。不包含第三方登入、細緻自訂權限、多店別、離線寫入佇列或自動衝突合併。

## 技術架構

- 使用 Supabase Auth 管理帳號、密碼與登入工作階段。
- 使用 Supabase PostgreSQL 作為唯一的中央營運資料來源。
- 使用 Row Level Security（RLS）將權限落實在資料庫層；前端畫面隱藏不是安全邊界。
- 保留 IndexedDB 作為唯讀離線快取與遷移前的本機備援；不再做多人資料的唯一來源。
- 不在前端放入 Supabase `service_role` 或其他祕密金鑰。

## 角色與權限

### 管理員（admin）

- 可管理帳號：建立店員、停用帳號、變更角色、啟動密碼重設流程。
- 可檢視成本、總庫存成本與所有營運資料。
- 可新增、編輯、刪除商品、客戶、報價、銷售與庫存異動。
- 可匯出／匯入資料與檢視稽核紀錄。

### 店員（clerk）

- 可掃碼銷售、查看可售庫存、建立客戶與報價。
- 不可檢視成本或總庫存成本。
- 不可刪除營運資料、管理帳號、匯入／匯出資料或檢視稽核紀錄。
- 店員停用後不得登入、讀取或寫入任何中央資料。

## 資料模型

- `profiles`：`id`（對應 Auth 使用者 UUID）、`display_name`、`role`（`admin`／`clerk`）、`active`、建立與更新時間。
- `items`：商品主檔；成本資料採管理員專用的安全查詢或拆分的受限資料表，不能透過店員可讀取的 API 回應取得。
- `inventory_transactions`：進貨、售出與盤點異動；包含品項、數量、備註、操作者、建立時間。
- `customers`、`salespeople`、`quotations`、`quotation_lines`：沿用既有業務資料並加入操作者與時間欄位。
- `sales`、`sale_lines`：訂單與多品項結帳明細；伺服器端交易必須檢查庫存後再扣減。
- `audit_logs`：帳號、角色、停用、刪除、庫存調整與資料匯入等重要行為的操作者、事件、目標、時間與必要摘要。

所有公開資料表均啟用 RLS，且明確設定 grants 與每一項讀寫政策。角色資料以受保護的 `profiles` 或伺服器端宣告為準，不以可由使用者自行修改的前端欄位或 user metadata 做授權依據。

## 使用流程

1. 使用者開啟系統先看到帳號／密碼登入頁。
2. 驗證登入後取得角色，依角色載入可用頁面與資料。
3. 管理員可在帳號管理建立或停用店員帳號；首位管理員由初始化流程建立。
4. 所有需要改變庫存的操作交由中央資料庫驗證權限與庫存；不可只依前端目前顯示的數量判斷。
5. 角色不足、帳號停用、網路中斷及庫存不足，均顯示明確可理解的錯誤原因。

## 遷移、同步與離線策略

1. 管理員在轉換前先從現有系統匯出 JSON 備份。
2. 管理員在受限的遷移流程中上傳／匯入資料；系統先驗證，再建立雲端保護備份，成功後才寫入中央資料庫。
3. 現有 IndexedDB 和 `localStorage` 保留不刪除，作為轉換後的本機回復備援。
4. 線上時，中央資料庫為權威來源；寫入成功後其他裝置透過重新載入或即時同步取得最新結果。
5. 第一版離線時只能檢視上次同步的庫存與客戶快取；不可結帳、進貨、編輯、刪除或建立報價／客戶。
6. 同時操作同品項時，中央資料庫交易重新檢查庫存；後送出且不足的操作被拒絕，不覆蓋先成功的操作。

## 安全與錯誤處理

- 所有前端連線僅使用公開 publishable／anon 金鑰與登入者工作階段；`service_role` 僅能存在於受信任的伺服器端環境。
- 每個資料表都以 RLS 限制對已登入且啟用帳號的存取；管理員專用欄位與查詢不可回傳給店員。
- 停用帳號時，同步撤銷工作階段，避免已登入的店員持續操作。
- 密碼不自行儲存或雜湊；交由 Auth 服務處理。
- 匯入、刪除、角色變更、庫存調整與結帳失敗時，不得部分覆蓋中央資料。

## 驗收條件

1. 不同電腦登入後可看到同一份最新資料。
2. 管理員可建立、停用店員並控制其角色；停用帳號無法繼續操作。
3. 店員無法透過畫面或直接資料 API 讀到成本，也無法刪除或管理帳號。
4. 多人同時銷售時，庫存永不低於零，且每筆操作都有操作者與時間。
5. 遷移前、遷移中失敗與遷移後均保留可回復的原本機資料與匯出備份。
6. 斷線時明確切換為唯讀模式；恢復連線後以中央資料庫資料為準。
7. 所有公開表的 RLS、grants、登入、角色、庫存交易與帳號停用皆有自動化或整合測試。
