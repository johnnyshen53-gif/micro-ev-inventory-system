# 月銷售業務員績效設計規格

## 目的與已確認決定

讓每筆新銷售在結帳時指定一位業務員，並讓店長按月查看各業務員的售出件數與銷售金額。結帳操作者與績效歸屬是不同資料，不以登入帳號推定業務員。一般員工維持現有月銷售總覽，但不得讀取個人績效資料。

- 一張訂單只歸屬一位業務員；結帳時必選啟用中的業務員。
- 第一版只計算售出件數與銷售金額，不計毛利、佣金、退貨或目標達成率。
- 月份採 `Asia/Taipei` 的月初含、次月月初不含區間；月總覽與績效使用相同口徑。
- 目前雲端沒有業務員與銷售紀錄。對可能在上線前產生的舊銷售，不自動猜測業務員；顯示為未歸屬，不列入個人績效，月總覽仍包含它們。

## 現況與方案選擇

`sales.created_by` 是結帳登入者，`salespeople` 是另一份名單；目前銷售沒有業務員欄位。月銷售頁的「業務員」欄實際顯示結帳帳號，應改標示為「結帳人」。雲端業務員名單目前可讀取，但畫面的新增、編輯、停用尚未寫回雲端。

不採用「在公開可讀的 `sales` 表加 `salesperson_id`，只靠畫面隱藏」的簡化方案；一般員工仍可透過資料 API 讀取歸屬。採用私有歸屬表與受保護的資料庫函式，保持現有一般員工月總覽可讀，同時把個人績效限制在店長。

## 資料與權限

- 在 `app_private` 建立每張銷售單一筆的歸屬資料：`sale_id`、`salesperson_id`、結帳當時的業務姓名快照。`sale_id` 唯一；業務員以穩定 ID 彙總，改名或停用不改變歷史歸屬。該表不暴露給 Data API，撤除 `anon`、`authenticated` 的直接存取，並啟用 RLS 作額外防護。
- 延伸現有原子結帳 RPC，增加必填業務員 ID。資料庫確認使用者是啟用員工、業務員存在且啟用，再於同一交易內寫入銷售、明細、序號、庫存異動、保固與歸屬；任何一步失敗全部回滾。舊的兩參數結帳入口不得繞過必填要求，應回傳明確的重新整理／選擇業務員訊息。
- 新增只供店長使用的月績效讀取 RPC：在資料庫再次檢查店長身分，依台灣月份區間統計各業務員的售出件數與銷售金額；一般員工與未登入者呼叫均拒絕。每張訂單的金額只加總一次，件數則加總該單所有明細數量，避免多明細重複計入總額。
- 補齊雲端業務員名單的建立、更新與停用：只允許店長寫入；新增時記錄實際登入者，更新不覆寫建立者。沿用現有讀取權限，使結帳員能選擇啟用中的業務員；登入帳號與業務員名單仍分開管理。

## 畫面與資料流

1. 店長在「業務管理」建立業務員，儲存成功後從雲端重新載入；跨裝置可見相同名單。
2. 「銷售管理」結帳處加入必填業務員選單，只列啟用者。名單為空或未選擇時阻止結帳並顯示可操作的提示；選定 ID 隨銷售明細送入原子 RPC。結帳成功後重新讀取雲端資料。
3. 「月銷售」保留目前件數、總額及明細；店長另見按業務員分組的績效表（業務員、件數、金額）。績效透過店長專用 RPC 載入，非店長不呼叫、不快取個人績效。現有操作帳號欄改稱「結帳人」，避免與績效歸屬混淆。
4. 停用業務員後不能再被新銷售選用，但既有績效仍可查詢。載入績效失敗時顯示錯誤，不把空白誤報為零績效，也不影響原本月總覽。

## 涉及範圍與驗收

- 資料庫：新增私有歸屬表、擴充結帳 RPC、店長專用統計 RPC，保留既有銷售 RLS 與一般員工月總覽。
- 前端：`index.html`、`app.js`、`inventory.js`、`cloud-data.js`；更新必要的快取版本號。新增／調整對應單元、介面與權限測試。
- 驗收：必填與停用業務員拒絕；多品項一單正確歸屬、金額不重複計算；銷售失敗不留半筆資料；跨裝置業務名單與績效一致；台灣月界線正確；一般員工無法透過畫面或直接 RPC／資料 API 讀取個人績效；完整測試通過。
- 實作與資料庫套用、Commit、Push、部署分開回報；未經使用者明確同意，不執行 Commit 或 Push。
